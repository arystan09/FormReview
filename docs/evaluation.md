# Stage 5: grouped offline extraction evaluation

This public synthetic benchmark is **not author-blind**, independently human-reviewed
truth, a live model experiment or evidence of generalization. Labels are pending
human review. Scripted replay numbers measure fixture behavior and coverage; the
regex baseline numbers measure a deliberately narrow labelled-line algorithm.
Exactly 10 mandatory product stages remain; no stage 6 work is included.

## Dataset and provenance

The manifests schedule exactly 48 supported documents: 16 families × 3 variants.
Ten complete families (30 documents) are dev; six (18) are test. Existing 12
walkthrough documents retain their bytes and paths. They are included, not added
on top of the 48. The three existing complete forms (01, 07, 12) form family f01.

| f02 | dev | NFC/BOM Unicode supplier; same identity across TXT variants |

Dev families are scenario/identity families sharing some basic field-label syntax;
this is not a claim of ten unrelated document designs. Held-out layouts and
identities do not occur in dev. Variants, identities and TXT/PDF counterparts stay
inside their family and split. This is a small, constructed benchmark, not a random
sample of supplier documents. Automatic leakage checks are exact raw/canonical
hashes, declared group/template/identity IDs, supplier/email/registration literal
identities and value-masked template fingerprints (fixture headings removed).
They do not establish absence of every possible semantic or stylistic similarity;
the human checklist below includes that audit.

`datasets/scenarios.json` contains explicit authored source records and expectations.
The 12 legacy expectations were adapted from the separately authored provisional
stage-2 labels, including explicit raw terms/status corrections. Other expectations
are written with their synthetic scenarios, not generated by the baseline, replay,
model, scorer, approval records or normalization function. The compiler shares
these authored scenario records when rendering sources and labels: this is disclosed
synthetic authorship, not independent annotation by another person. It invokes the
parser only to locate specified quotes/values and derive canonical offsets/hashes.
Review by a human remains pending for all 48 documents.

`gold.json` is separate from each manifest's source entries. Versioned strict
Pydantic schemas and exported JSON schemas define statuses, accepted raw values,
accepted normalized values, normalizable booleans, expected validation flags and
exact page/quote/value offsets. NFC/newline canonicalization comes from the product
parser. Gold anchors must be unique, bounded and exact. Manifests pin gold/raw/
canonical hashes. Gold missing fields have no candidates; ambiguous fields have two.
A malformed email or complex/out-of-range term is **present**, with its literal,
evidence and expected unresolved flag. It is not relabelled missing.

Unsupported files are outside both manifests in `fixtures/parser_negative/`.
Stage 5 adds a mixed digital/textless PDF and an explicitly unsupported-extension
file (a synthetic sentinel, not a real DOCX). Existing scan/encrypted/malformed/
empty/oversize-page fixtures remain separate. There is no OCR.

## Freeze and holdout policy

`datasets/configs.v1.json` freezes full executable replay prompt/model/settings/
schema/normalizer/evidence versions and the baseline settings, plus implementation
hashes. The actual replay request is built from this file; the baseline receives
only canonical pages and its frozen settings. No labels, IDs, manifest metadata,
reviewer decisions or manual approved values are sent to either provider. Replay
alone may look up its explicitly labelled historical script by source hash.

The freeze was created before any test extraction outputs. Stage 5 permits test
source/label/hash validation only: the evaluate runner rejects extraction on the
test split. No test output was used to tune a prompt or baseline. Future authorized
experiments must version/freeze changes before final test execution and disclose
any holdout exposure. These files are auditable hashes, not a tamper-proof registry.

## Matching and denominators

All matching is exact after the product's canonicalization. No case-folded or fuzzy
value credit, country inference, ID punctuation removal, email repair, or implied
payment terms. Accepted aliases must each have an explicit gold anchor. Terms use
only lexical NetN/Ndays in 0–365. Ambiguous candidate order is ignored, but a
one-to-one match of both expected candidates is required for full candidate credit.

A candidate matches only if its raw literal is accepted, its unique server-derived
value span matches an expected anchor on the same page, its normalized value matches
with the exact type, and its validation flags match. An enclosing quote can differ
from the gold quote if it uniquely anchors the same value span. A quote for the
wrong entity earns no field credit, even if its text exists verbatim.

The offline validator reuses explicit term normalization and Django email validation.
`invalid_email` is an evaluation validation flag; this stage does not change the
product's normalization version. Unnormalizable-handling scores include this server
validation behavior, not evidence that a provider itself reasoned about validity.

| Metric | Denominator and success rule |
| --- | --- |
| present_field_accuracy | Scheduled gold-present **normalizable** fields; status, literal, source span, normalized value and flags all match |
| present_literal_evidence | All scheduled gold-present fields; correct present status, literal and source span, irrespective of normalization |
| unnormalizable_handling | Scheduled gold-present unnormalizable fields; correct literal/source, null normalization and expected flag |
| missing_handling | Scheduled gold-missing fields; completed output correctly declares missing |
| ambiguity_detection | Scheduled gold-ambiguous fields; completed output declares ambiguous |
| ambiguous_candidates | Scheduled gold-ambiguous fields; both candidates fully match |
| evidence_validity | Per-field max(expected candidate count, predicted count); credit for each unique valid predicted quote/value occurrence, regardless of entity truth |
| all_five_correctness | Every scheduled document; all five fields fully match, including missing/ambiguous/unresolved handling |

Reports store integer numerators/denominators and rates; zero denominators yield
JSON null, not zero or a fabricated perfect score. Missing fields never enter
present-field accuracy. Failed/refused/unattempted cases remain scheduled and
contribute zero success to every applicable gold denominator. Unexpected extra
results are rejected. Manual/unknown-mode results become errors, never model credit.
Errors use fixed sanitized codes; reports contain no source text, emails, quotes,
keys or full prompts. Provider, dataset, config, freeze, scorer, validator and build
provenance accompany every report. The build hash covers relevant source files,
lockfile and dataset compiler/specification. No timestamps/random IDs are needed
for reproducible reports. Existing report paths are never overwritten by the CLI.

## Run and reproduce

From the project root, with Python 3.12 and uv installed:

```sh
uv sync --frozen --all-groups
uv run python -m scripts.build_dataset
uv run python manage.py evaluate --help
uv run python manage.py evaluate --dataset datasets/test/manifest.json --validate-only
uv run python manage.py evaluate --dataset datasets/dev/manifest.json --provider baseline
uv run python manage.py evaluate --dataset datasets/dev/manifest.json --provider replay
```

No database, worker, key, model SDK request or network call is needed for evaluate.
The SDK dependency remains installed for the pre-existing live product path.
The deterministic compiler uses existing pypdf and standard Helvetica references;
it embeds/downloads/distributes no font software and adds no dependencies.

Default report artifacts are `outputs/evaluation-v1-dev-baseline.json` and
`outputs/evaluation-v1-dev-replay.json`. They already exist in this handoff. For a
new run, pass a new path, for example `--output work/baseline-check-001.json` or
`--output work/replay-check-001.json`; existing output paths fail explicitly.

Run `make check`, `make integration`, `uv run pytest -m e2e` and
`uv run python scripts/demo_smoke.py` for regression verification. Integration and
browser checks require disposable PostgreSQL 18/UTF-8 with CREATEDB and installed
Chromium; evaluate itself does not. Docker/container/Linux memory proof and remote
CI remain separate verification gates. No paid benchmark is part of stage 5.

## Dev examples and measured fixture outcomes

- Wrong entity: f07_v2 contains buyer `Country: Germany`, while the supplier is
  `Supplier country = Spain`. The baseline quotes Germany correctly but fails
  supplier-country accuracy. Evidence validity alone remains true.
- Missing: f03_v1 omits registration ID, country and terms. Correct missing statuses
  count under missing handling, never inflate the present-field denominator.
- Ambiguous: f04_v1 supplies sales and billing contact emails. Both are expected
  candidates. Choosing only one fails ambiguity detection and full field credit.
- Malformed-but-present: f05_v2 retains its malformed email and complex terms with
  `invalid_email`/`unresolved_terms`, separate from normalizable-field accuracy.

On dev, baseline completes 30/30 cases and gets 29/30 all-five matches. It gets
112/113 normalizable-present matches, 7/7 unresolved handling, 24/24 missing,
6/6 ambiguity detection and 132/132 quote-validity slots. Replay completes only
its existing 12 scripted cases: 18 are unattempted. Across all 30 scheduled cases,
it gets 10/30 all-five, 45/113 normalizable-present, 2/7 unresolved, 8/24 missing,
2/6 ambiguity and 51/132 evidence slots. These are synthetic fixture checks,
not a baseline-versus-live-model comparison or an accuracy/generalization claim.
